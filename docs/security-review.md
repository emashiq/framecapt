# Security and reliability review (phase 09)

Date: 2026-10-02. Reviewed: the code as committed after phase 08 plus the changes of this phase (everything below cites
`file:line` of the tree after the fixes). Method: every `handle(...)` registration and every `sendEvent` call was read in
full, then each preload, window, session, protocol, filesystem and child-process path; findings were fixed in code with
regression tests where they were medium or higher (and for most low ones), the rest are documented as residual risk.

Companion documents: `docs/performance.md` (benchmark), `docs/architecture.md` (process model), `docs/recording-persistence.md`
(session format and recovery policy), `docs/decisions.md`.

## 3. IPC: every channel

Chokepoint: `handle()` in `src/main/ipc.ts:40` is the **only** place that touches `ipcMain` (a test fails if any other
file calls `ipcMain.on/once/handle/...`). Per call it checks, in order: (1) the sender is a registered `webContents` with
an allowed role (`getRole`), (2) the frame is the **top** frame and its URL is inside the app (`checkSender`,
`src/main/ipc-core.ts:34`, `isAppUrl` in `src/main/app-origin.ts:16`: `file:` below the renderer folder, or the dev-server
origin in development), (3) the payload parses with the channel's strict schema (`runChannel`, `ipc-core.ts:56`); anything
the handler throws that is not an `IpcError` becomes a generic `INTERNAL`. The handler roles must be a subset of the
contract's, and a test requires equality. `tests/unit/ipc-security.test.ts` runs the role/frame matrix against **all 116
channels** (every role x top/sub frame x good/foreign URL).

Roles: `main` = the app window (its tabs are the editors, ADR-050), `overlay` = selection overlays, `toolbar` = recording controls, `recorder` = the hidden
capture window, `countdown` = the 3-2-1 window, `camera` = the camera bubble. Payload column: field names of the strict schema; `bytes` fields are
`ArrayBuffer` with a size cap. "Path?" says whether the request can carry a path, URL or command: **no** unless stated.

## 4. Preload, navigation, permissions, CSP

- **Preload** (`src/preload/index.ts`): one object, `framecapt`, with `invoke` (name checked by `isIpcChannel`, an `own-property`
  test that also rejects `__proto__`/`constructor`; only the first argument is forwarded) and `on` (`isIpcEvent`; the
  listener receives the **payload only**, never the `IpcRendererEvent`; returns an unsubscribe). `ipcRenderer` itself is
  not exposed. Tested by loading the real preload with a recording `electron` (`ipc-security.test.ts`, "preload"), and in
  the packaged app (`npm run smoke:packaged`: bridge keys are exactly `invoke,on`, no Node globals, unknown channel refused).
  Prototype pollution: payloads are validated by strict schemas that never merge into existing objects; 400 rounds of random
  junk including `{"__proto__": ...}` leave `Object.prototype` untouched (same file).
- **Window preferences** (`src/main/windows.ts:110`): `contextIsolation`, `sandbox`, `webSecurity` true; `nodeIntegration`,
  `webviewTag`, `allowRunningInsecureContent`, `spellcheck` false; `devTools` only when unpackaged; `nodeIntegrationInWorker`,
  `nodeIntegrationInSubFrames` and `experimentalFeatures` are not set and default to false in Electron 44 (`electron.d.ts`).
  Every window (main, overlay, toolbar, countdown, hidden recorder) is built from `securePreferences()`; `app.enableSandbox()`
  (`src/main/index.ts:36`) covers any future one. Tested: `window-security.test.ts`.
- **Navigation** (`src/main/security.ts:15-35`), registered once on `app.on('web-contents-created')` so it covers **every**
  webContents (main, overlays, toolbar, countdown, recorder, any future one): `will-navigate`, `will-redirect` and
  `will-frame-navigate` are cancelled unless the target is an app URL; `will-attach-webview` is cancelled;
  `setWindowOpenHandler` denies everything. There is **no `shell.openExternal`** anywhere in `src` (grep), so there are no
  external links to validate; `shell.openPath` is only used for history media (S-03) and the chosen output folder
  (`settings:openOutputDir`, a main-owned path). `shell.showItemInFolder` takes main-owned paths (R-01).
- **CSP** (`src/shared/csp.ts`): `default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:
blob: framecapt-media:; media-src 'self' blob: mediastream: framecapt-media:; font-src 'self'; connect-src 'self'; base-uri
'none'; form-action 'none'; frame-ancestors 'none'; object-src 'none'`. Delivered **both** as a response header
  (`installCsp`, `security.ts:46`, dev server) **and** as a `<meta>` tag injected at build time
  (`vite.renderer.config.ts`); since phase 10 the `app://` protocol handler also sends the policy as a response header. Development adds only the dev-server origin and an
  inline script for React refresh (`devCsp`); the packaged app was checked to carry the meta tag (smoke test). The one
  loosening is `style-src 'unsafe-inline'` (R-03).
- **Permissions** (`security.ts:59-99`, `app-origin.ts:67-86`): request and check handlers allow only `media`, `clipboard-sanitized-write` and `fullscreen` (the History video player; `main` window only), and only for app
  URLs. The microphone is allowed for every app page; video (the camera) depends on the window's registered role: a
  request (`getUserMedia`) only from `recorder` and `camera`, a check (device labels for `enumerateDevices`, Settings) also from
  `main`; an unregistered window, overlay, toolbar and countdown get neither (`isPermissionAllowed` in `app-origin.ts`, `roleOf` from `windows.ts`; tests in `app-origin.test.ts`, `window-security.test.ts`).
  The camera bubble window is content protected, so it is never captured; the camera is composited into the video by the recorder (ADR-042). Everything else is denied: geolocation, web notifications (the app's own OS notifications are made by main, `desktop.ts:155`, with fixed text), MIDI, HID, serial,
  USB, Bluetooth, clipboard-read, fullscreen (except the `main` window), pointer lock, idle detection, `display-capture`, `openExternal`... (table test).
  Display capture is not a permission prompt: `setDisplayMediaRequestHandler` (`capture/display-media.ts`) answers only
  from a main-made one-shot grant bound to the requesting webContents/top frame/app URL, otherwise `{}`. Device choosers
  are cancelled (S-08).
- **No remote content, no network**: the renderer loads `file:` assets and `framecapt-media:` only (fonts are bundled);
  `connect-src 'self'` and the session blocker (S-08) cancel every http(s)/ws(s)/ftp request, so there is nothing to
  upload, update-check or report to. Verified in the packaged app: a `fetch('https://example.com')` from the page fails.
  There is no telemetry code (`grep -rn "fetch(\|XMLHttpRequest\|WebSocket" src` finds nothing).

### `framecapt-media:` (`src/main/recording/media-protocol.ts`)

Privileges: `standard, secure, stream` only (no `bypassCSP`, no CORS, no fetch API). Resolution
(`resolveMediaUrl`, line 68) accepts exactly five shapes and nothing else: `//<registry id>` (a recording this run wrote),
`//thumb/<history id>` and `//file/<history id>` (+ one optional lowercase `[0-9a-z]{1,24}` cache-busting segment),
`//vproject/<history id>/<sha256>.<ext>` (section 16) and `//flowstep/<history id>/<index>` (section 17). The id
is a uuid matched by a regex **before** any lookup; the lookup is a `Map` get (main-made ids -> main-known paths). No
query, hash, user, port, extra segment, path or drive letter can name a file, whatever its encoding (`%2e%2e`, `%5c`,
double-encoding, UNC, absolute drive paths: 30+ shapes in `media-protocol.test.ts`, each answered 404/400 with
`Cache-Control: no-store`, none reaching the disk). The response is served only for `.webm .mp4 .mkv .png .jpg .jpeg`
and only for **regular files**; GET/HEAD only (405 otherwise); `Range` is a single `bytes=a-b | a- | -n` range parsed by
`range.ts` (anything else is ignored, an unsatisfiable start is 416, the end is clamped to the file). There is no listing:
the scheme has no index route.

## 5. Filesystem, child processes, fuses, mocks, logging

**Write locations** (all main-chosen): `userData/recordings/<uuid>/{manifest.json, stream.webm}` (manifest: temp file, fsync,
rename; stream: append handle, fsync on close), `recordings/completed/<id>.json`, `userData/history/{history.json, thumbs/}`
(`writeFileAtomic`: temp, fsync, rename, `src/main/shots/atomic-write.ts:9`), `userData/shots/<uuid>/original.png`,
`userData/settings.json` (atomic, debounced), `userData/logs/main.log` (2 MB rotation), `userData/diagnostics/` (R-04), and
the **user-chosen** screenshot/recording/MP4 locations, which come only from main-process save/folder dialogs (plus a write
probe, `settings/output-dirs.ts:30`). Finished recordings are published by `rename` of a partial file in the same folder;
an existing file is never overwritten (`freeTarget`). Exports use a `.partial` name made by main.

**Deletions** (every `rm`/`trashItem` in `src/main`): a session folder whose name is a uuid inside the recordings root
**and** is a real directory (not a link) **and** whose manifest names the same id (`recovery.ts`, `session-service.ts:dirFor`),
the single `.framecapt-<id>.partial.webm` a manifest names when it equals the expected name (and is absolute), screenshot
session folders by uuid (`shots/session-store.ts`: containment re-checked, `sweep` uses `Dirent` so links are skipped,
7-day age, `keep` marker), thumbnails by `<uuid>.png`/leftover patterns (`history/thumbs.ts`), and temp files this call
made. **User files are only ever moved to the Recycle Bin** (`shell.trashItem`, `history/service.ts:360`), on an explicit,
confirmed action; "remove from history" never touches the file; nothing deletes an export. `fs.rm` on a link removes the link.

**FFmpeg** (`src/main/media/ffmpeg.ts`): the binary path comes only from `resolveFfmpeg` (packaged:
`resources/ffmpeg/win32-x64`; development: `vendor/ffmpeg/...`; never PATH, never renderer input); `spawn(file, args,
{ shell: false, windowsHide: true, stdio: ['ignore','pipe','pipe'] })` with argument **arrays** (line 168); inputs and
outputs are absolute main-made paths (`mediaPath`), so they can never start with `-`; inputs are opened with
`-protocol_whitelist file` and a forced demuxer where the format is known (S-02); every run has a timeout (remux 10 min,
probe 30 s, export `max(10 min, 4 x duration)`) and an `AbortSignal`; abort/timeout kill the **tree** (`taskkill /T /F`).
After a main-process crash ffmpeg exits by itself (its progress pipe closes): measured in the failure-mode exercise (4a:
no orphan 0.6 s after the kill). The only other `spawn` is the Squirrel installer hook (`src/main/squirrel.ts:18`,
`shell:false`, fixed arguments).

**Fuses** (`forge.config.ts:41-46`, read back from the packaged exe with `npx @electron/fuses read`): RunAsNode off,
cookie encryption on, `NODE_OPTIONS` off, `--inspect` off, embedded asar integrity on, only-load-from-asar on;
`GrantFileProtocolExtraPrivileges` is **off** since phase 10 (S-13/R-02 fixed: the UI is served from `app://framecapt`). `asar: true`. DevTools are disabled when packaged.

**Mocks and test hooks in production** (all gated on the build-time constant `__FRAMECAPT_E2E__`, which is the literal `false`
in every normal build, so the branches and the dynamically imported mock module are removed from the bundle): mock capture

fake/taken shortcuts, mock displays), the `__frameCaptTest` global and the IPC call counter. `npm run check:mocks` fails on any
of them in `.vite/build` (main **and** preload), `.vite/renderer` and the packaged `out/**/app.asar`. Result on the
production build: `check-no-mocks: OK (3 bundle files and 1 app.asar scanned, no mock or test-hook markers)` (also asserted
before every benchmark run); the E2E build is checked with `--expect-mock` as a positive control; the script itself is tested
(`check-no-mocks.test.ts`). `FRAMECAPT_USER_DATA_DIR` (tests) is ignored by packaged builds (`src/main/index.ts:41`).

**Logging**: `log.*` receives statuses, codes, sizes and durations. Reviewed for capture content (none), clipboard content
(none; clipboard writes are not logged), window titles (never logged; not stored, S-05), absolute paths (only in error text
from the OS or ffmpeg, and those are home-redacted, S-06). `Blocked navigation to` logs scheme+host only. The native test
"main log never contains capture content" (`tests/native/capture.native.spec.ts:705`) passes. Evidence JSON written by
tests/benchmarks is redacted by `tests/native/evidence.ts` (user name, window titles).

## 13. Phase 10 changes (packaging, app:// scheme, updates)

- **R-02 closed.** The production renderer is served from `app://framecapt` (`app-asset.ts`: pure resolver; `app-protocol.ts`: handler). The scheme is `standard` + `secure` only. The resolver refuses other schemes/hosts/ports/credentials, dot segments (checked on the URL as written, because the URL parser folds `/a/../x` silently), percent-encoded and double-encoded traversal, backslashes, NUL, `:`, empty segments and unknown extensions, and re-checks containment after `path.resolve`. Unit tests (`tests/unit/app-asset.test.ts`) cover these cases; an e2e test fetches refused URLs through the real handler; `isAppUrl` (IPC sender checks, permissions, display-media authorization, navigation lockdown) accepts exactly `app://framecapt`.
- **Fuse off.** `GrantFileProtocolExtraPrivileges` is disabled in `forge.config.ts`; `smoke:packaged` and `smoke:installed` read the fuse back from the exe and load the UI.
- **Installer defects found by running it.** (1) Squirrel downloaded an `<iconUrl>` from raw.githubusercontent.com during install: an offline machine waited about 85 s; removed (ADR-034). (2) `--squirrel-firstrun` was treated as an obsolete hook and quit the app; it now starts normally. (3) The launch-at-login entry is removed on uninstall (needs a ready app, so the hook waits for `ready`).
- **Network.** Neither the app nor its updater makes a request: the update adapter is `unconfigured` (no autoUpdater call); 60 s runs of the e2e build and of the installed app saw zero non-loopback TCP connections, no request outside app/framecapt-media/blob/data schemes, and nothing for the network blocker to cancel. The only network access during packaging is the build-time FFmpeg and Electron downloads (hash-pinned).
- **Not changed / open.** The installer and executables are UNSIGNED, so Windows SmartScreen will warn (owner action: certificate). Squirrel's own stub (about 3.8 MB) remains after uninstall. CI actions are pinned to major versions, not SHAs (hardening option). Signing and a configured update feed were not exercised (no certificate, no feed).

## 15. Multi-source recording and the `.fcap` container (2026-10-07)

Reviewed by the implementer only; the lead engineer reviews the diff.

- **New channel `history:extractFcap`** (role `main`, request `ExtractFcapRequestSchema`, strict): `{ id: history uuid, sourceIndex: 0..3 | null, startMs, endMs: ints within 24 h, endMs > startMs, format: 'mp4' | 'webm' }`. By id only: main looks the item up, requires `type: recording, format: fcap`, re-reads and validates the header, checks the source index against it and clamps the end to the recorded duration. The output name is made in main (`<name> - <Screen 1|All>[ (n)].<ext>` next to the `.fcap`, a free name, never overwriting); no path, crop rectangle or ffmpeg argument comes from the renderer (the rectangle is read from the header). It shares the export queue (one ffmpeg job at a time) and uses `export:cancel` and the `export:*` events (kind `extract`); `export:progress/done/failed` carry no paths beyond the existing done event. ffmpeg is spawned with `shell: false` and an argument array through the common `-protocol_whitelist file` input helper.
- **`recorder:start` `target: 'multi'`**: `sources` 2..4 `SourceIdSchema` ids (`^(screen|window):\d+:\d+$`), unique, strict objects; `sources` is accepted only with `multi` and required for it. Every source is checked against a fresh `desktopCapturer` listing in main, twice (before the countdown and after the selection step); capture still goes through the usual one-shot, webContents-bound grants (granted one source at a time). Engine messages stay closed sets: `prepare` carries the sources (`EngineMultiSourceSchema`, strict, 2..4), `prepared` the tile rectangles (max 4), and `tileLost { index 0..3 }` is a strict event of the `recorder` role.
- **Window titles (S-05 extended)**: the manifest, the `.fcap` header, the completion record, history and logs carry only `Screen n` / `Window n` and a source count. `controller.ts` keeps the real names only in memory for the selection step. Tests: `recorder-multi.test.ts` (a manifest of a session that records a window called "Secret plan.docx - Word" does not contain it), `recording-multi.spec.ts` (header bytes and session record).
- **`framecapt-media:` serves a payload window of `.fcap` files** (`media-protocol.ts`): the route shapes are unchanged (registry id, `thumb/<id>`, `file/<id>`); `.fcap` joins the served types, answered **only** from `payloadOffset` for `payloadLength` bytes as `video/webm` after the header was validated against the file size (the header bytes are never sent, ranges are clamped to the payload, `416` reports the payload length). An invalid or truncated header is `404`. Regular files only, GET/HEAD only, `no-store`, as before. Tests: `media-protocol.test.ts` (offset math, suffix ranges, 416, HEAD, damaged header), `range.test.ts` (`planMediaSlice`).
- **File parsing**: `parseFcapHeader` is strict and bounded (reads at most 4096 bytes; JSON length <= 64 KB and before the payload; zod `strictObject`; sources 1..4 inside the picture; fixed `payloadOffset`, `payloadType`); it never trusts a length past the real file size. Cases in `fcap.test.ts`. A `.fcap` found by rescan or chosen with Locate must pass it before it is listed or served.
- **History actions**: `history:open` still opens only `.png .jpg .jpeg .webm .mp4` (`isOpenableMedia`), so the shell is never asked to launch an `.fcap`; the UI opens its own details view instead. `history:saveCopy`, `history:startDrag` and `history:reveal` work on the file as for any item.
- **Temporary files**: `.framecapt-<sessionId>.fcap.partial` (output folder) and `remuxed.webm` / `.remux.partial.webm` (session directory) are removed on every path; recovery deletes only the partial whose name carries the session id and equals the manifest's plan (existing rule).
- **Not a protection**: the container is not encrypted; the payload is a plain WebM. It keeps casual players and file managers from opening it, nothing more (ADR-041).
- **Residual**: a malicious `.fcap` placed in the output folder by another program is parsed by the strict reader and decoded by Chromium/ffmpeg like any WebM; the usual media-decoder exposure applies.

## 16. Video editor (P8, P9: 2026-10-07)

- **Channels** `video:open`, `video:save`, `video:export`, `video:addImage`, `video:pickAudio` (role `main`; strict zod) and events `video:exportProgress`, `video:exportDone`, `video:exportFailed` (the output path appears only in `video:exportDone`, like `export:done`). Cancel reuses `export:cancel` on the shared job queue.
- **The renderer never names a file.** Main resolves the source from the history id; the output goes next to it under a name main picks (`<name> (edited).<ext>`). A project is a recipe, at most 512 KB, every number bounded. Pictures and audio files are **assets**, `<userData>/video-projects/<historyId>/assets/<sha256 hex>.<ext>` (extension from a fixed list); an item refers to one only by its sha256 id, and `ASSET_NAME`, the store and the media route all accept only that shape. An audio file comes from an Open dialog in main, is size-capped (100 MB), copied through a temporary file, and must pass ffprobe (an audio stream, at most two hours) or it is deleted again. A picture is validated as PNG (magic bytes, size within the frame limit) and stored under the hash of its bytes.
- **Nothing the renderer sends is put into the ffmpeg command as text.** The filter graph is made only of integers, fixed-precision seconds and the validated `#rrggbb` colours of redact boxes; it is written to a file in a per-job temp folder (removed afterwards) and read with `-/filter_complex`. **Text** is drawn by the renderer into a transparent PNG (the same code as the preview); main checks each picture (PNG magic, exactly the item's size, one per text item, at most 40, 8 MB each) and writes it into the temp folder. The text, a font name or an audio file's name never reach the graph or the arguments (`edit-graph-overlays.test.ts` asserts this with hostile strings). Extra inputs are opened with `-protocol_whitelist file`, paths made by main (a temp file or an asset path built from a validated id); pictures are looped with fixed numbers (`-loop 1 -framerate <n> -t <seconds>`).
- **Preview assets** are served by `framecapt-media://vproject/<history id>/<sha256>.<ext>`: the history item must exist, the name must match `<64 hex>.<ext>` and the content type is whitelisted (images and audio); a query, fragment, extra segment or another name is a 404 (`video-assets-route.test.ts`). Range requests work (audio seeks).
- **Project files** are only for ids shaped like history ids inside that folder (atomic write; a damaged or newer file is set aside, never deleted) and are removed with the history item. Unused assets are pruned (right at open; at a save only when older than ten minutes, so Undo still works).
- **Redaction** boxes are drawn into the exported pixels by ffmpeg; the preview is only a view of them. The recording itself is never modified.
- **A `.fcap` can be opened** (P11): still only by history id. `video:open` reads its header (`readFcapHeaderCached`, validated) and returns the layout (`layout`, names generic, no window titles); the probe and the export read it through `mediaInputArgs` (the same fixed options as the extract: file protocol only, `-skip_initial_bytes`, Matroska forced). The "Source" choice only sets the project's crop to a tile of that layout; the export is a normal MP4, WebM or GIF.

## 19. Capture library: folders on disk (2026-10-07, ADR-048)

- **New channels** (role `main` only, strict zod): `library:tree`, `library:createFolder`, `library:renameFolder`, `library:deleteFolder`, `library:moveContentsUp`, `library:moveItems`, `library:setCaptureFolder`, `library:reveal`; event `library:changed`. The security tests require the `library:` family to be main-only, include samples in the extra-key and strict-object walks, and refuse traversal payloads (`tests/unit/ipc-security.test.ts`).
- **Path validation argument.** The renderer sends no path. A folder is a relative name from a strict grammar enforced by the shared schema (`LibraryFolderSchema`, `src/shared/library.ts`): `/`-separated, 1 to 8 levels, 1 to 80 characters per level; no `< > : " / \ | ? *`, no control characters (so no drive letter, UNC prefix, backslash or alternate stream), not `.` or `..`, no leading dot, no trailing dot or space, no Windows device name (also with an extension), not a step-guide folder name. Main then resolves it under the fixed roots (`resolveFolder`, `src/main/library/paths.ts`): `path.resolve(root, ...segments)` and a containment check that rejects a result whose `path.relative(root, target)` is empty, starts with `..` or is absolute. The check is repeated in main even though the schema already refuses such input (defence in depth; tests call the service directly with `../escape`). History ids are uuids; a move works on the item's own path, which main took from History.
- **Links.** Folder listing and rescan use `Dirent` (a link or junction is reported as a link and is neither listed nor entered, S-07); create, rename, delete, move-up and move check each existing level with `lstat` and refuse a link, so nothing is created or moved through a junction that points outside the capture folders (tests with real junctions).
- **No deletion of user files.** `library:deleteFolder` removes a folder only when it is empty on disk in both roots (only `desktop.ini` and `Thumbs.db` are removed with it, with a non-recursive `rmdir`) and History lists nothing in it. Moving never overwrites (free name). A cross-volume move copies without overwriting, verifies the size, and only then moves the original to the Recycle Bin; if that fails, the copy is removed and the original stays.
- **Atomicity.** A rename renames in both roots and rewrites all history paths in one atomic `history.json` write; any failure renames back what was renamed (tests: second root fails, history write fails). `library.json` and `general.captureFolder` are updated after; `captureFolder` is validated by the settings schema (an invalid stored value makes the file fail validation and be set aside like any other bad settings) and ignored by `saveDir` if it would escape its root.
- **Drag and drop.** Cards carry only history ids in a custom drag type (`application/x-framecapt-items`); the drop target sends them to `library:moveItems`, which validates them. A plain drag no longer starts the OS file drag (Alt+drag does), so a card cannot be dropped as a file into FrameCapt's own folder pane.

## 20. The editors are tabs of the main window (2026-10-07, ADR-050; reverses ADR-047)

- **No `editor` role any more.** ADR-047 briefly gave the editors a window of their own with a seventh role; ADR-050 removed it. `ROLES` is `main, overlay, toolbar, recorder, countdown, camera` again, `#/editor` is not a role (an unknown hash renders the main app), no window is made for an editor and nothing is stored about one (the remembered-bounds file and its parser are gone). Every screenshot, video, step-guide, settings, history and library channel is the `main` role's alone, exactly as before ADR-047 (`ipc-security.test.ts` and `ipc-contract.test.ts` pin it, and a test checks that every other role is refused on the editor channels). `fullscreen` is granted to the main window only (the Library's video player).
- **Opening a tab is main's decision.** `editor:open` carries a session id or a history id (plus a step index); main checks that the session or item exists, tells a screenshot from a recording or a guide, takes the tab title from the item's file name and sends `editor:openTab` to the main window; a request made before the window's renderer is listening waits in a queue that `editor:ready` hands over. The renderer never names a path or a title. A picture the user opens, drops or pastes is a session main made from validated PNG bytes (`shot:importImage`), and opens directly.
- **The unsaved-work guard is the main window's again.** `editor:setState { dirty }` (a boolean: `dirty` also covers a running video export) feeds `CloseGuard`, which asks via `editor:confirmClose`; `editor:resolveClose` answers. A quit or a close without close-to-tray asks about unsaved tabs; closing to the tray only hides the window and leaves the tabs open. A second close attempt still goes through (a hung renderer can never trap the user), and `session-end` never waits. Closing the main window deletes the originals of the sessions its tabs held (`discardSync`); sessions are tracked in main, never named by the renderer.
- **Dialogs** (Open image, Save as, Add audio) are parented to the main window (`dialogParent`); the paths still never leave main.
- **The renderer rules did not change.** Tabs are mounted in one renderer under the same CSP and origin checks; a hidden tab is `inert` and takes no keys. The Library's folder sidebar width and view options are kept in the browser storage as conveniences (never read as anything but a number or one of a few strings, parsed with defaults).

## 21. Concurrent recordings, live panels and meeting capture (2026-10-10, ADR-051 to ADR-053)

- **New channels, all zod-validated with sender checks like the rest.** Recorder: `recorder:toolbarMenu` (toolbar; opens a native menu, `menu` is an enum), `recorder:stopAll` (main), `recorder:addPanel` (main, toolbar), `recorder:removePanel` (main, toolbar), `recorder:setPanelHidden` (main), `recorder:panelMenu` (main). Meetings: `meeting:respond` and `meeting:getPrompt` (role `meeting-prompt` only), `meeting:list`, `meeting:record` and `meeting:addToRecording` (main). Events: `meeting:prompt` (main to the prompt window) and `meeting:state` (main to the main window). No channel carries a path, a window title or a native handle from the renderer: panels and meetings are named by recording id and source id, and main re-validates the source against a fresh listing.
- **New role `meeting-prompt`.** The prompt card is a frameless, non-focus-stealing, content-protected window that can only read its own prompt and answer it. A response for a prompt that is gone is ignored.
- **koffi (ADR-052).** The first runtime native module: an unsigned `.node` addon loaded in the main process, lazily and inside a try/catch. A Windows Defender Application Control or AppLocker policy may block it; the load then fails and the fallback probe takes over (no crash). Signing the release build covers the addon. Only fixed user32, dwmapi, kernel32 and advapi32 functions are bound.
- **Child process.** The fallback microphone probe runs `reg.exe query` through `execFile` with an argument array, `shell:false`, `windowsHide` and a 3 s timeout; its output is parsed, never executed.
- **Window titles in memory only (S-05).** Titles and class names are read to recognize a meeting. They are not written to disk, to the log or into manifests (panels get generic names such as "Panel 2") and not sent to a renderer except the app label ("Google Meet"). The log says only which probe loaded.
- **Residual risks.** English-only signatures can mistake a window whose title imitates a meeting for one; the worst case is a prompt the user can dismiss. Nothing records without a click, except the "Add it to the recording" share setting, which only adds a source to a recording the user already started. Concurrent recordings are capped at three (`MAX_CONCURRENT_RECORDINGS`).
