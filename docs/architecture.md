The renderer uses `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, `webSecurity: true`. There is no remote content: every window shows the bundled UI only.

## Build layout (Electron Forge + Vite)

`forge.config.ts` registers `@electron-forge/plugin-vite` with three builds:

- main: `src/main/index.ts` -> `.vite/build/main.cjs`
- preload: `src/preload/index.ts` -> `.vite/build/preload.cjs`
- renderer `main_window`: `src/renderer/index.html` -> `.vite/renderer/main_window/`

`package.json#main` is `.vite/build/main.cjs`. When `MAIN_WINDOW_VITE_DEV_SERVER_URL` is defined (`npm start`) the window loads the Vite dev server; otherwise (packaged build, `electron-forge package` output used by e2e) it loads `app://framecapt/index.html`: the built renderer is served from a privileged custom scheme by `src/main/app-protocol.ts` (resolver with strict containment in `src/main/app-asset.ts`, ADR-033), not over `file://`.

## Preload and IPC model (Implemented)

`src/shared/ipc-contract.ts` is a single object map: `channel -> { request (zod), response (zod), roles }`. Types for `invoke` are derived from it. Phase-01 channels:

| Channel           | Request                                                          | Response                                                          | Roles |
| ----------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------- | ----- |
| `app:getInfo`     | none                                                             | `{ version, electron, chrome, node, platform, arch, isPackaged }` | main  |
| `app:reportError` | `{ source, message<=2000, stack<=8000?, componentStack<=8000? }` | void                                                              | all   |

Events (main -> renderer) are a separate allowlist (`app:themeChanged`).

Call path for `window.framecapt.invoke(channel, payload)`:

1. Preload: rejects anything not in the contract (`UNKNOWN_CHANNEL`, using `Object.hasOwn`), then `ipcRenderer.invoke`.
2. Main `ipc.ts#handle(channel, { roles }, handler)`:
   1. `event.sender` must be a registered webContents whose role is allowed for the channel;
   2. `event.senderFrame` must be the top frame and its URL must be the app origin (dev: the Vite dev server origin; production: a file inside the built renderer directory);
   3. the payload is parsed with the channel's zod schema;
   4. the handler result is wrapped as `{ ok: true, data } | { ok: false, error: { code, message } }`. Unexpected errors are logged in main and replaced by a generic message, so raw errors never reach the renderer.
3. The pure parts (`app-origin.ts`, `ipc-core.ts`) have no Electron imports and are unit tested.

`handle` also refuses, at startup, to register a handler whose roles are broader than the contract's.

The preload never exposes `ipcRenderer`, Node APIs or arbitrary channels. Sandboxed preloads can only require a small `electron` subset, so shared code (the contract, including zod) is bundled into `preload.cjs` by Vite.

## Screenshot workflow (phase 03, capture source revised in phase 04: Implemented, verified on the host)

```
Home (main window)                     main process                              overlays ('overlay', one per display)      hidden worker ('recorder', fallback only)
 Screen / Window / Region  --start-->  CaptureFlow.start  (BUSY if a flow runs)
                                       region / pick-display: create the overlay windows HIDDEN (opacity 0) now,
                                         their renderers load while the next steps run -> overlay:getInit waits
                                       hide main window, wait 'hide' + 200 ms
                                       region:  desktopCapturer.getSources({ thumbnailSize: max physical size })
                                                one call, every display, size verified == physical size
                                                (a display that fails: worker:grabFrames ---------------------------------------------> getDisplayMedia frame)
                                       overlays.setFrames -> showInactive at opacity 0 -> raw BGRA frame ----> paint on a canvas,
                                                                                                    overlay:ready -> opacity 1 + focus
                                       <---------- overlay:confirm / pickDisplay / cancel -------------------- user selects
                                       crop the frozen NativeImage (pixels) or grab the picked display
                                       write userData/shots/<id>/original.png, close ALL overlays
 shot:ready -> editor   <----------   show + focus main window, shot:ready, capture:flowEnded
```

- **Pixel-exact capture source (phase 04, ADR-014)**: screen and region screenshots come from `desktopCapturer` images in MAIN (`capture/exact-capture.ts`), not from `getDisplayMedia` video frames (4:2:0: about one pixel of chroma bleed on saturated edges, measured in phase 03). ONE `getSources({ types: ['screen'], thumbnailSize: { width: max physical width, height: max physical height }, fetchWindowIcons: false })` call serves all displays (Electron fits each thumbnail into the box keeping its aspect, so asking for the largest dimensions means nothing is downscaled); sources are mapped to displays by `display_id`, and an image is accepted only when `getSize()` equals the display's physical size EXACTLY. Otherwise that display falls back to the worker's `getDisplayMedia` frame and a warning is logged. Window screenshots first take the worker's video frame to learn the window's size, then request a window thumbnail at exactly that size; when the size matches the thumbnail is used (pixel-exact), otherwise the video frame is kept. The path that ran is logged (`Screenshot path: ...`, `Freeze-frame: n/n screens exact`). `getDisplayMedia` stays the capture method for recording. The E2E mock build skips this path (synthetic frames come from the worker).
- **Capture worker** (`windows.ts#getWorkerWindow`, `worker.ts`, `views/RecorderWorker.tsx`): one hidden `BrowserWindow` (role `recorder`, `show: false`, `backgroundThrottling: false`, the same secure web preferences), created on first use and destroyed when the main window closes. Since phase 04 it is the FALLBACK for screenshots (a display whose exact image failed verification, the window size probe, the E2E synthetic frames) and will own recording in phase 05. Main sends the event `worker:grabFrames { requestId, sources }`; the worker acquires each source in turn through the existing `capture:grant` + `getDisplayMedia` path (`acquireDisplayStream`, no audio), grabs one frame with `grabFullResolutionFrame`, stops the tracks, and answers with the invoke `worker:frameResult { requestId, frames[{ sourceId, width, height, png }] }` or `worker:frameError`. Main validates sizes (PNG <= 150 MB, dimensions <= 16384), accepts only the sources it asked for, and times a request out after 10 s. Only role `recorder` may call `worker:*`.
- **Shot sessions** (`shots/session-store.ts`): `ShotSession { id (uuid), kind, width, height, createdAt, originalPath }`. The original PNG lives in app-owned `userData/shots/<id>/original.png`, never in a user folder and never memory-only. `discard` deletes only that directory (the id must match the uuid pattern and the resolved path must be inside the shots root); `discardSync` does the same while the app is closing. At startup, session directories older than 7 days without a `keep` marker are removed; only counts are logged. The renderer sees metadata and bytes through `shot:get`, never the path. **Lifecycle (phase 04)**: the session is created when the capture completes; the editor opens it with `shot:get` (main remembers it as the editor's session); it is deleted when the editor closes (Done, Discard, leaving the Capture tab, or closing the app window). A successful save or copy does NOT delete it, so the user can keep editing and save again. A crash leaves the directory for the 7-day sweep.
- **Overlays** (`overlay.ts`, `views/overlay/`): one frameless, always-on-top (`'screen-saver'` level), non-resizable, non-movable, no-shadow, `skipTaskbar` window per display, `bounds = display.bounds` and set again after creation (Electron's mixed-DPI placement quirk), then read back with `getBounds` (a mismatch is logged); `setContentProtection(true)` as a second line of defence. The first overlay to paint takes keyboard focus; if all overlays lose focus the flow is cancelled. Region mode shows the frozen frame full-bleed on an opaque window; pick-display mode uses a transparent window with a highlight and a "Click to capture this screen" card. **Phase 04 latency work**: the windows are created hidden (opacity 0, never shown) at the start of the flow, so their renderers load while the main window hides and the screens are grabbed; they are shown (`showInactive()`, still at opacity 0) only AFTER the grab, because a never-shown window's renderer is throttled to about one frame per second (the "painted" signal, a double `requestAnimationFrame`, then took 1-2 s on some overlays); `overlay:ready` sets the opacity to 1. A never-shown window cannot be in a capture, so the "frames are grabbed before any overlay is visible" invariant holds. The frozen frame travels as raw BGRA bytes (`NativeImage.toBitmap()`, ~20 MB for 3440x1440) and is painted on a canvas (`shared/pixels.ts#bgraToRgba`); encoding it as PNG cost ~110 ms per screen in main plus a decode in each renderer.
- **Region mode** is freeze-frame: the main window is hidden and every display is grabbed BEFORE any overlay is visible, so nothing of the selection UI can be in the pixels. The selection (local DIP) is mapped to frame pixels by `overlayRectToFramePixels` using the ACTUAL frame size ratio (`src/shared/geometry.ts`), rounded outward and clamped; selections under 2x2 px are refused. The crop is `frozenNativeImage.crop(pixelRect)` (the frame is a `NativeImage` kept in main, scale factor 1). Dragging on another display clears the first display's selection (`overlay:selectionStarted` -> `overlay:clearSelection`). The pointer is clamped to the overlay's display, so a selection cannot leave it ("Selections stay on one screen").
- **Pick-display mode** (Screenshot > Screen with more than one display): overlays are closed, the screen settles for 200 ms, then the picked display is grabbed. With exactly one display no overlay is shown and the screen is captured at once.
- **Window mode**: the renderer shows a source picker dialog (`components/SourcePicker.tsx`, native `<dialog>`), main hides the main window and the worker grabs that window source. A 0-size or entirely black frame, a failed grab, or a window that vanished between listing and capture ends with "That window is minimized or can't be captured. Restore it and try again."
- **Flow state** (`shots/flow-state.ts`, `capture-flow.ts`): a second `capture:startScreenshot` while a flow runs fails with `BUSY`. Every path ends in exactly one `finish`: close all overlays and frozen frames, restore and focus the main window, then emit `shot:ready` (on success) and `capture:flowEnded { outcome: 'cancelled' | 'completed' | 'error' }`. Display changes while overlays are open (`display-added`, `display-removed`, `display-metrics-changed`) cancel with `DISPLAYS_CHANGED`. The renderer refocuses the button that started the flow when the flow ends without a result.
- **Export** (`shot-handlers.ts`): `shot:export` validates PNG/JPEG magic bytes and a 200 MB cap, shows `dialog.showSaveDialog` (parent: main window; default folder `Pictures/FrameCapt`, default name `FrameCapt YYYY-MM-DD at HH.mm.ss.png|jpg`) and writes atomically (temp file in the same folder, then rename). `shot:copy` validates PNG bytes and writes the image with the Electron 44 promise-based `clipboard.write([new ClipboardItem({ 'image/png': blob })])` (there is no `clipboard.writeImage` in this version). `shell:showItemInFolder` accepts only paths exported by FrameCapt in this run. Since phase 04 the renderer sends the FLATTENED bytes of the editor (below) through these channels; main never sees annotations and never reads the original for export.

Channels added in phase 03 (main window): `capture:startScreenshot`, `shot:get`, `shot:export`, `shot:copy`, `shot:discard`, `shell:showItemInFolder`. Overlay role: `overlay:getInit` (now waits for the frames), `overlay:ready`, `overlay:selectionStarted`, `overlay:confirm`, `overlay:cancel`, `overlay:pickDisplay`. Recorder role: `worker:ready`, `worker:frameResult`, `worker:frameError`. Events: `shot:ready`, `capture:flowEnded`, `overlay:clearSelection`, `worker:grabFrames`. Added in phase 04 (main window): `editor:setDirty { dirty }`, `editor:resolveClose { discard }`; event `app:confirmClose`. `OverlayInit.image` is now raw BGRA bytes (`imageFormat: 'bgra'`).

Geometry that could not be exercised physically on the build host (both displays scale 1, primary at 0,0): mixed DPI, negative origins, rotation. These are covered by unit tests (`tests/unit/geometry.test.ts`: scales 1/1.25/1.5/2, a display at (-1920,-300), mixed-DPI pair, 90/270 rotation, frame size different from bounds x scale) and by the E2E mock build, whose two displays have scales 1 and 1.5, a negative origin and a frame size (3440) that is not bounds x scale (2293 x 1.5).

## Screenshot editor (phase 04: Implemented; pixel checks verified on the host and in the E2E build)

The editor replaces the phase-03 result view and runs in the main window's renderer. It is an internal Canvas 2D implementation (ADR-015), no canvas framework.

| Part      | Code                                                                                                                                                 | Notes                                                                                                                        |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Model     | `src/renderer/editor/model/` (`types`, `commands`, `history`, `hit-test`, `geometry`, `arrow`)                                                       | Pure TypeScript, no DOM, unit tested. All geometry is in IMAGE PIXELS of the original capture.                               |
| Flatten   | `src/renderer/editor/flatten.ts` (pure, on a Canvas2D-like `DrawContext`), `export.ts` (OffscreenCanvas: `flattenToBlob`, `flattenThumbnail`, fonts) | The same `renderDoc` produces the export in Chromium and runs against Skia (`@napi-rs/canvas`) in the unit tests.            |
| View math | `src/renderer/editor/view.ts`                                                                                                                        | `screenToImage` is the single pointer conversion; unit tested for zoom/pan/DPR combinations.                                 |
| UI        | `src/renderer/views/editor/` (`EditorView` state and shortcuts, `EditorStage` canvas/pointer/text, `EditorToolbar`, `OptionsStrip`)                  | One visible canvas redrawn on demand; no animation loop while idle (e2e counts `requestAnimationFrame` calls while idle: 0). |

**Model.** `Annotation` = `arrow { from, to, color, width }` | `rect { rect, color, width }` | `text { at, text, color, fontSize, fontWeight }` | `redact { rect }`; `EditorDoc { width, height, annotations, crop: Rect | null }`. A redaction has NO color and NO opacity field; the reducer rebuilds it from its rectangle only and ignores any other patch field. `apply(doc, command)` is a pure reducer (`add`, `update`, `remove`, `setCrop`, `reorder`) that returns the SAME object for no-ops. `History { past, present, future, gesture }` holds immutable documents (structural sharing), at most 200 undo entries, and merges commands that carry the same gesture key into one entry (a drag, or a run of arrow-key nudges). Crop is non-destructive: `setCrop` stores an integer rectangle clamped to the image, annotations keep original coordinates, undo/redo restores it, and the editor dims everything outside the crop (the whole image stays visible and editable).

**View and DPR.** `View { zoom, panX, panY }`: `zoom` is DEVICE pixels per image pixel (1 = 100% = the capture 1:1 on the screen's pixels at any devicePixelRatio), pan is in CSS px. Zoom range 10%-800%, fit-to-view by default (never above 100%), Ctrl+wheel zooms at the cursor, Space/middle-drag pans. The canvas backing store is stage size x devicePixelRatio, so lines and handles stay crisp; nothing but the view transform knows about zoom or DPR.

**Flatten and redaction rules (ADR-016).**

1. `renderDoc(ctx, base, doc, { forExport: true })` draws the crop rectangle of the base image (`drawImage` source rect), then the annotations in z-order translated by -crop, then ALL redactions LAST: a redaction can never be undercut by a later arrow, rectangle or text ("Redactions always cover everything beneath", also shown as a tooltip).
2. A redaction is `#000000` at alpha 1, `source-over`, drawn with integer coordinates. Its rectangle is snapped outward to whole pixels and grown by one more pixel on every side, so no half-blended original pixel survives at an edge.
3. JPEG: compression smears a hard black edge across the 8x8 luma and 16x16 (4:2:0) chroma blocks it passes through. Measured on random noise at quality 0.92, black pixels deviated by up to 37 levels (up to 14 px from the edge); even quality 1.0 left 14 (chroma upsampling reaches across block borders). For JPEG the cover therefore grows to the 16 px block grid of the OUTPUT image plus a 2 px margin (`jpegRedactionCoverage`), so every block touching the user's rectangle is entirely black. Measured: every pixel under the drawn rectangle is 0 in a Chromium-encoded JPEG. The cost: JPEG redactions cover up to 17 px more per side than the PNG ones (the Save menu says so).
4. Export size = crop size or full image size; never scaled by zoom or devicePixelRatio. Text uses Inter (bundled; `document.fonts.load` runs before flattening) with a font size in image pixels, so the export matches the editor at any zoom.
5. Save and Copy send the flattened PNG/JPEG (JPEG quality 0.92) to `shot:export` / `shot:copy`. The original is retained only in the app-owned session directory for editing; an exported file is the redacted artifact and is never the original unless no edit changed anything. `flattenThumbnail(base, doc, maxWidth = 480)` renders the flattened output (crop and redactions applied) and is the ONLY thumbnail source the history view (phase 07) may use.

**Opened pictures and image layers (document schema 3).** `shot:openImage` (File > Open image, Ctrl+O) shows a main-process Open dialog and returns the file's name and bytes after a size cap and a magic-byte check (PNG, JPEG, WebP, GIF, BMP); the renderer decodes any of them, re-encodes PNG (`editor/decode.ts`) and `shot:importImage` starts an ordinary session of kind `import` (history source `unknown`). It is never auto-saved: the after-capture setting is for captures. Dropping a file on the window or pasting on the Capture view goes through the same renderer path (DOM events, no clipboard permission). Inside the editor the `image` annotation (`rect`, `assetId`, `radius`, `opacity`, `shadow`) draws a picture stretched to its rectangle; `assetId` is the SHA-256 of the picture's PNG bytes, so a picture inserted twice is stored once. Pictures come from `editor:pickImage` (dialog), `editor:historyImage` (an owned screenshot by history id), paste or a drop on the canvas; the renderer keeps up to 32 pictures / 64 MB (`editor/assets.ts`) and only the ones the document still uses are saved. The project payload carries them (`assets: [{ id, png }]`); `ProjectStore` re-hashes each, checks PNG magic and size, writes `projects/<id>/assets/<sha256>.png` before `project.json`, deletes stale files, and returns the valid ones on `shot:openFromHistory` (`edit.assets`). A layer whose picture is missing draws a neutral placeholder. Image layers are flattened below the redactions, which stay on top.

**Unsaved changes.** `dirty` = the document differs from the one last saved or copied (a fresh capture is dirty until its first save/copy; undoing back to the saved state is clean). Done, Discard, leaving the Capture tab and closing the window with a dirty editor ask "Discard this screenshot?" in a Radix AlertDialog (focus trapped, focus starts on "Keep editing"). Closing: the renderer reports `editor:setDirty`; main intercepts the window's `close` (`main/close-guard.ts`): clean -> close; dirty -> keep the window, send `app:confirmClose`, and the answer arrives as `editor:resolveClose { discard }`. A second close while the question is open always goes through (a hung renderer can never trap the user), `session-end` (logoff/shutdown) is never held up, and `app.exit()` bypasses it. No `beforeunload` is used. Keyboard shortcuts live in the editor view only and are ignored while typing in an input, textarea or open menu, or while a dialog is open.

**Accessibility.** The top bar is a `role="toolbar"` with a roving tabindex (arrow keys, Home/End), every control has an accessible name, tool and save/copy changes are announced in an `aria-live="polite"` region, focus rings are visible, and the options strip uses `radiogroup`/`radio` for colors, stroke and text size.

## Recording (phase 05: Implemented; native checks verified on the host, see capture-feasibility.md)

### Ownership

```
 main window / toolbar / (later tray, shortcuts)
        | recorder:start | pause | resume | stop | cancel | toggleMute | resolveChoice | reset
        v
 MAIN: RecorderController (src/main/recorder/controller.ts)  <- the ONE authoritative state
   pure machine (src/shared/recorder-machine.ts) -> recorder:state snapshot broadcast
        |  recorder:engineCommand (prepare | start | pause | resume | stop | abort | mute | levels | cursor)
        v                                           ^ recorder:engineEvent (prepared | needsChoice | started | stopped | sourceLost | trackEnded | levels | error)
 hidden 'recorder' window: RecorderEngine (src/renderer/recorder/engine.ts) - the only MediaRecorder
        | session:appendChunk {sessionId, seq, bytes}  (ack before the next)   | session:finish {sessionId, lastSeq}
        v
 MAIN: SessionService (src/main/recording/session-service.ts) -> userData/recordings/<id>/{manifest.json, stream.webm}
```

- **State is owned by main** and only broadcast: every window renders `recorder:state` snapshots (`status`, `activeMs` + `runningSince` for a live timer, `audio`, `muted`, `lost`, `choice`, `countdown`, `result`). Commands from any UI go through main, so a stop from the toolbar, the main window, closing the toolbar, a lost source and quitting the app are the same idempotent operation.
- **One recorder.** `RecorderEngine` asserts there is no other active MediaRecorder (`activeRecorderCount()`), commands run strictly in order, and every terminal path calls `releaseAll()`: tracks, audio context, level timer, crop timer and recorder are all released. `window.__frameCaptResources()` (read-only counters in the recorder window) lets the tests assert zero live tracks / audio contexts / loops / recorders after every recording.
- The recorder window is the phase-03 worker with `backgroundThrottling: false`. Measured: a hidden, never-shown window records at about 30 fps with this setting (see capture-feasibility.md).

### State machine

States: `idle -> selecting -> preflight -> countdown -> starting -> recording <-> paused -> stopping -> processing -> completed | error`. selecting, preflight, countdown and starting go back to `idle` on CANCEL or STOP. Events: START_REQUESTED, SOURCE_SELECTED, PREFLIGHT_OK, PREFLIGHT_NEEDS_CHOICE, COUNTDOWN_DONE, STARTED, PAUSE, RESUME, STOP, CANCEL, SOURCE_LOST, WRITE_FAILED, FINALIZED, FAILED, RESET, plus three extras: STOPPED (the engine flushed: stopping -> processing), MUTE_SET and AUDIO_LOST (a source's mute flag and "device gone" flag are part of the state). An event that is not valid in a state returns the same state with `rejected: true` and never throws; STOP in stopping, processing and completed is an accepted no-op. `activeDurationMs` is accumulated from monotonic timestamps of the running segments only, so paused time is never counted (wall clock is kept separately as `startedAt`). tests/unit/recorder-machine.test.ts checks every event in every state against a written-out table, plus the required scenarios (rapid start/stop, stop during countdown, cancel during starting, duplicate stop, pause/resume in the wrong state, source lost while paused, write failure while recording, reset after completed/error) and 200 random event sequences.

### Start-up flow

1. START: main minimizes the main window (a minimized window is not capturable; it stays in the taskbar so the user can find it).
2. selecting: a window comes from the picker; a screen is the only display, the `displayId` in the request, or the pick-display overlay; a region uses the overlay in `record-region` mode: **live**, not frozen (transparent window, 45% dim around the selection, the desktop keeps running underneath), button "Record" (Enter). The overlay is closed before anything is recorded, so it can never be in the output. The overlay IPC is routed to the recorder or the screenshot flow by `SelectionHost`. The region is mapped to display pixels with `overlayRectToFramePixels` and rounded down to even x, y, width, height.
3. preflight (`prepare` in the engine): enumerate microphones, acquire the display stream (with loopback if asked), acquire the microphone (`echoCancellation` and `noiseSuppression` on), build the canvas pipeline and the audio mix. Anything the user asked for that is not there is a **choice**, never silence: system audio without a loopback track ("System audio isn't available": record without it / cancel), a microphone id that is not in `enumerateDevices` (use the default microphone / record without a microphone / cancel), a denied microphone (record without / cancel), a microphone that cannot be opened. The main window is brought back for the question and minimized again after the answer.
4. countdown (optional 3-2-1): a transparent, click-through, content-protected, non-focusable window on the recorded display. Esc cancels through a global shortcut that is registered only while the countdown runs. Reduced motion is respected by the global `prefers-reduced-motion` rule. The window is closed (plus a 120 ms settle) before the recorder starts.
5. starting: the session directory is created, the engine starts the MediaRecorder (timeslice 1000 ms), the toolbar is shown.

### Video and audio pipeline

display stream -> canvas (`createCanvasTransform`: crop to the region and/or fit the 1080p preset, drawn from a self-correcting timer, so the frame rate is constant even on a static screen) -> `canvas.captureStream` video track. Quality presets: "1080p" fits inside 1920 x 1080 keeping the aspect ratio with even sides, never upscaling (3440 x 1440 -> 1920 x 804); "Source" keeps the native size. Frame rate 30 (default) or 60. Video bitrate 8 Mbps at 1080p30, scaled with pixels and frame rate (2.5-30 Mbps), Opus 128 kbps. Microphone and system audio each go through their own GainNode (mute = gain 0, not `track.enabled`), an AnalyserNode (levels) and into one MediaStreamAudioDestinationNode: one mixed track, nothing is ever connected to the speakers. Levels are sampled at 10 Hz only while recording and only while main says a toolbar is visible. A microphone or system track that ends, or a `devicechange` that removes the microphone, is reported once (`trackEnded`): the recording continues with the other sources, the toolbar shows a badge ("Microphone disconnected"), the main window shows a toast.

**Compositor and follow mouse (phase P4).** `createCanvasTransform` is a one-tile wrapper over `createCompositor` (`src/renderer/capture/compositor.ts`): tiles of `{ stream, src?, dst }` are drawn into one canvas per tick (timer or `requestVideoFrameCallback` driver, same keep-alive and cleanup as before); `src` is asked again every tick, while `dst` and the output size are fixed when the first frames arrive. The layout math is pure (`src/shared/compositor-layout.ts`: `followCrop`, `mosaicLayout`, `cameraRect`, unit tested) so the webcam overlay and multi-source mosaics can reuse it. Follow mouse (`options.follow.zoom` 1.5, 2 or 3, whole-screen recordings only) captures the unscaled frame and records a window of frame/zoom pixels (even sides) fitted to the quality preset; the window center eases toward the mouse (exponential smoothing, time constant 180 ms, frame-rate independent, 10 % dead zone) and is clamped inside the frame. The mouse comes from main: a 30 Hz timer in the controller (started after `STARTED`, stopped on every end path) reads `screen.getCursorScreenPoint()`, converts it to 0..1 of the recorded display and sends `{ cmd: "cursor", nx, ny }` to the engine only when it changed; on another display the last position is held.

### Chunk protocol and session files

- Renderer: `ChunkUploader` numbers chunks from 0 when they are pushed, reads each Blob only when it is its turn, sends `session:appendChunk` and waits for the acknowledgement before sending the next (strictly serial, ordered). The queue is bounded at 16 chunks or 64 MB: a chunk that does not fit is not accepted, the uploader fails with `QUEUE_OVERFLOW`, the recorder stops, and the chunks accepted so far are still written. Nothing is dropped silently and nothing is buffered without bound. A failed write halts the uploader.
- Main (`SessionService`, hardened in phase 06): validates the owner (only the recorder window that created the session may write), the session (exists, `recording` or `stopping`), size (1 byte to 16 MB, the IPC schema enforces the same cap; `CHUNK_TOO_LARGE`) and sequence (exactly last + 1; the previous chunk again with identical length and SHA-1 is acknowledged without a second write; a gap is `SEQ_GAP`; any other duplicate is `DUPLICATE_MISMATCH`); every rejection is logged without content. Operations of a session run through a promise chain (strict order even with overlapping invokes). It writes with a real `FileHandle.write` loop and acknowledges after the write. ENOSPC/EDQUOT map to `DISK_FULL`, everything else to `WRITE_FAILED`; the session is then closed, marked `failed` (with `error`) and `truncated` and kept. `manifest.json` (zod schema, `src/main/recording/manifest.ts`) is rewritten atomically (temp file, fsync, rename) at most every 5 s or 10 chunks and at every state change; a failing manifest update never loses a chunk. Backpressure high-water marks (renderer queue, main queue, slowest write) are in `manifest.stats`.
- Stop: main marks the session `stopping` (it still accepts the last chunks), the engine calls `recorder.stop()`, waits for the final `dataavailable` AND the acknowledgement of every chunk, then `session:finish {sessionId, lastSeq}`; main verifies `lastSeq`, fsyncs, closes and sets `state: "stopped"`. Then `SessionService.finalize` remuxes with FFmpeg and publishes (next section); the old raw-copy `publish` is gone.
- The published file is the **remuxed** WebM (phase 06): it has a container duration and a seek index (verified on the host: `ffprobe format.duration` is a number, Cues present, seeking decodes). Only the last-resort raw copy after a failed remux lacks them (`unindexed`, said so in the result view).
- Failures while recording (queue overflow, disk full, recorder error) stop the recording, keep what was acknowledged and publish it with a notice ("The recording stopped early"). A source loss does the same without an error. A recording shorter than one video frame (a few milliseconds) has no data and ends in the error "too short to save".

### Persistence, finalization and recovery (phase 06)

Files: `src/main/media/ffmpeg.ts` (resolve, run, probe), `src/main/recording/{manifest,session-fs,session-service,finalize,recovery,recovery-handlers}.ts`, `src/shared/recovery-ipc.ts`, `src/renderer/components/RecoveryBanner.tsx`. Full design: docs/recording-persistence.md.

- MediaRecorder output is one WebM byte stream cut at arbitrary points, so chunks are only ever appended, in order, to one `stream.webm`. The live file has no Duration or Cues; finalization remuxes with `ffmpeg -c copy -map 0 -f webm` into `.framecapt-<sessionId>.partial.webm` in the output folder, probes it (video stream and duration > 0), renames it to a free `FrameCapt YYYY-MM-DD at HH.mm.ss.webm`, and only then marks the session completed, writes `completed/<id>.json` and deletes the session directory including `stream.webm` (no duplicate copy).
- A failed remux keeps `stream.webm` (manifest `failed`, `finalize.log`); when the raw stream shows a video stream it is copied out as a last resort and the result says "Saved without a seeking index".
- Startup (`RecoveryService.startup`): interrupted `finalizing` sessions get their matching partial file deleted (only the exact path the manifest names, whose file name carries the session id) and the remux re-run once; leftovers of finished/discarded sessions are removed; everything else with data is a candidate. The Capture view shows one card per candidate (Recover, Discard with confirmation, Details). Unreadable manifests are kept as `manifest.corrupt.json` and the session is treated as `unknown` (still recoverable).
- Channels: `recovery:list | recover | discard | reveal` (main window only, session ids only, refused while a capture runs) and the event `recovery:changed`. Discard deletes only a uuid directory inside `userData/recordings` whose manifest names the same id.
- E2E-build-only hooks (compiled out of normal builds, markers checked by `check-no-mocks.mjs`): `FRAMECAPT_E2E_FREE_BYTES_FILE`, `FRAMECAPT_E2E_FFMPEG_DELAY_MS`, `FRAMECAPT_E2E_QUIT_CAP_MS`.

### Windows and playback

- **Toolbar** (`toolbar` role, `#/toolbar`): a 48 DIP high frameless always-on-top pill, `skipTaskbar`, `setContentProtection(true)`, draggable by the grip only (`-webkit-app-region`), timer (active time, `h:mm:ss` after an hour), pause/resume, stop, per-source mute and meter, warning badge; paused shows an amber dot and "Paused"; stopping/processing show "Saving..." (or "Finishing recording..." while the app quits). Placement (`src/shared/toolbar-placement.ts`, unit tested): whole screen or window = bottom-center of the display's work area (above the taskbar), 24 DIP up; region = just below the region, else above, else on another display, and only as a last resort (single display, region fills it) inside it. Width follows the recorded audio sources and grows when a source is lost.
- **Main window during recording**: minimized (and a close request only minimizes it) and restored when the recording is over. The result view shows a player (`<video>` on `framecapt-media://<id>`), duration / size / dimensions / audio badges, Show in folder, Copy path, New recording.
- **`framecapt-media:`** (`src/main/recording/media-protocol.ts`): a privileged (standard, secure, stream, fetch) scheme registered before ready. It serves ONLY files main produced (an unguessable id -> path map) with Range support implemented from the file (`Content-Range`, 206, 416; parser unit tested), and `framecapt-media:` is allowed in `media-src` only, in both CSPs.
- **Quit**: `before-quit` while recording or paused stops and finalizes first (toolbar: "Finishing recording..."), with a hard cap of 15 s (`settleWithin`, `src/main/recorder/quit-cap.ts`). Past the cap the running ffmpeg is killed (abort signal -> `taskkill /T /F`), the app quits, and the manifest stays `stopping`/`finalizing`; the next start deletes the matching partial file and re-runs the remux once (verified end to end in tests/e2e/recovery.spec.ts with a 1.5 s cap and a delayed remux). Before recording started it is a cancel.

Channels added in phase 05: `recorder:start | pause | resume | stop | cancel | toggleMute | getState | resolveChoice | reset | showInFolder | copyPath` (main window; the toolbar may pause, resume, stop, cancel, mute and read state), `recorder:engineEvent`, `session:appendChunk`, `session:finish` (recorder window only). Events: `recorder:state`, `recorder:levels`, `recorder:engineCommand`. New role `countdown`. New IPC error codes: SEQ_GAP, SEQ_CONFLICT, CHUNK_TOO_LARGE, SESSION_INACTIVE, WRITE_FAILED, DISK_FULL.

## Local history and MP4 export (phase 07: Implemented; verified in unit, E2E and native runs)

Files: `src/main/history/{store,thumbs,query,files,service,export-service,handlers}.ts`, `src/main/media/export.ts`, `src/shared/history-ipc.ts`, `src/renderer/views/HistoryView.tsx` + `views/history/*`, `components/{Mp4Export,RecentCaptures}.tsx`, `src/renderer/history/*`.

- **Metadata only, apart from the files.** `userData/history/history.json` is `{ version: 1, backfilled?, items[] }` (zod, newest first, written through `writeFileAtomic`: temp file, fsync, rename; writes are serialized). A damaged or unknown-version file is renamed `history.json.corrupt-<time>`, the history starts empty, the reset is logged, and `history:consumeNotice` tells the UI once ("History was reset because its file was damaged. Your files were not touched."). At most 1000 items: the oldest fall off the list, their files are never touched. An item is `{ id (uuid made in main), type, createdAt, path, width, height, durationMs, sizeBytes, format, thumbnail (`<id>.png` or null), hasAudio, source, derivedFrom }`.
- **Items are added only by main when it produces an output**: `shot:export` (screenshots, with the thumbnail the editor sent), the recorder controller after finalization, recovery (recovered or resumed recordings, `createdAt` = the recording's start), and a finished MP4 export (a separate item with `derivedFrom`). Saving the same file again refreshes its item (same id). On the first run with history (no `history.json` at all, never after a reset) the recordings that have a `completed/<id>.json` record and an existing file are added once (newest 200).
- **Thumbnails** (`userData/history/thumbs/<id>.png`): screenshots use ONLY the PNG the editor draws from the flattened result (`flattenThumbnail`, redactions applied, at most 480 px wide); main validates PNG magic, size (2 MB) and the width in the IHDR, and never derives one from the original capture (without a thumbnail the entry shows a placeholder). Recordings get one frame from ffmpeg (`-ss min(1, duration/2) -frames:v 1 -vf scale=min(480\,iw):-2`, through a partial file and a rename) in the background, serially; the entry exists before its thumbnail does and `history:changed` reloads the lists. The folder is bounded: thumbnails nothing refers to are deleted (never files that are not named `<uuid>.png`; young `.partial.png`/`.tmp` leftovers are kept for 60 s because a write may still run), and above 200 MB the oldest items lose their thumbnail first.
- **Listing**: `history:list { filter?, query?, limit? }` stats the matching files with a concurrency of 8 and returns `exists` and the current size; `query` words must all match the name, type, format, source or the date (ISO and long English forms). Missing files stay listed as "File moved or deleted" with Locate... (an open dialog in main; the pick must have the entry's extension AND content: PNG/JPEG magic bytes, or an ffprobe video of the right container; a file already listed elsewhere is refused) and Remove; `history:clearMissing` removes every missing entry.
- **Actions** (all by history id, role `main`; no path ever comes from the renderer): `history:open` (`shell.openPath`), `reveal` (`showItemInFolder`), `copyImage` (screenshots only, at most 200 MB; PNG bytes as they are, a JPEG is re-encoded by `nativeImage`), `copyPath`, `remove` (entry only; main remembers the entry for 15 s so `undoRemove` can restore it, the thumbnail survives that window), `deleteFile` (a separate action, confirmed in the UI by name; `shell.trashItem` moves it to the Recycle Bin, never an unlink; if the Recycle Bin refuses nothing changes; a file that is already gone only removes the entry), `relink`, `clearMissing`, `saveCopy` (recordings: save dialog, copy through a temp file and a rename, refuses the original's own path).
- **MP4 export** (`src/main/media/export.ts`, `export-service.ts`): capability is detected once at startup from `ffmpeg -encoders` (`libx264` AND the native `aac`) and cached (`export:capabilities`); without it the UI says "MP4 export needs an FFmpeg build with H.264 — your recording is saved as WebM", `export:mp4` is refused with `FFMPEG_MISSING`, and no file is ever produced under a false name. `export:mp4 { historyId }`: main resolves the source from history (WebM recordings only), asks for the destination in a save dialog (default `Videos/FrameCapt`, same base name, `.mp4` enforced), and returns a job id; `export:progress`, `export:done`, `export:failed` events carry the history id so the UI can show the state wherever the user is; `export:cancel` aborts. One export at a time (the encoder uses every core; a second request is `BUSY`). The encode goes to `.framecapt-export-<random>.partial.mp4` next to the destination, is verified (`ffprobe`: MP4 container, H.264, AAC when the source had audio, duration within 0.5 s), and renamed onto the destination. Cancel, failure, timeout (max(10 min, 4x duration)) and a failed check delete only that partial file; the source is only ever read. Quitting during an export cancels it and waits (5 s cap) for the partial file to go. Details and flags: docs/ffmpeg.md.
- **Media protocol** (`framecapt-media:`): in addition to `//<registry id>` (this run's recordings) exactly two history routes exist: `//thumb/<history id>` and `//file/<history id>`. Anything with a query, a fragment, a port, user info, extra path segments or an id that is not in history is a 404, and only the content types the app produces are served (`webm, mp4, mkv, png, jpg`). The CSP gained `framecapt-media:` in `img-src` (still absent from `script-src`, `connect-src`, `style-src`, `font-src`).
- **UI**: History is a wide view (header with count, All / Screenshots / Recordings, search) over a responsive card grid (roving tab stop; arrow keys, Home/End; Enter opens the details; Delete removes from history with a 5 s Undo toast and never touches a file; focus returns to the card). The details view has a larger preview (image, or a `<video controls>` on the file route), metadata, every action, and the inline MP4 export (progress, Cancel, result, retry). The home view shows the latest 6 items; the recording result view offers the same MP4 control. Export state lives in a small external store, so progress survives leaving the tab.
- New IPC: `history:list | consumeNotice | open | reveal | copyImage | copyPath | remove | undoRemove | deleteFile | relink | clearMissing | rescan | saveCopy`, `export:capabilities | mp4 | cancel` (all `main` role), events `history:changed`, `export:progress | done | failed`; `shot:export` takes an optional `thumbnail`.
- E2E-build-only hook (compiled out of normal builds): `FRAMECAPT_E2E_NO_H264=1` behaves like a build without an H.264 encoder.

## Video editor (core: trim, cuts, masks, crop, fades, volume, export)

Files: `src/shared/{video-edit,video-edit-history,video-ipc}.ts` (model, undo history, IPC schemas), `src/main/media/{edit-graph,edit-export}.ts`, `src/main/video-projects/{store,service,handlers}.ts`, `src/renderer/views/video-editor/*`, `src/renderer/history/video-export-store.ts`.

- **Model (`video-edit.ts`, pure, shared by renderer and main).** A `VideoProject` v1 is a recipe next to the recording, never a copy: `{ sourceId (history id), source {durationMs, width, height, hasAudio, fps?}, trim, cuts[], crop, items[], audio {volume 0..2, muted}, fadeInMs, fadeOutMs, export {format, scale?, gifFps?} }`. **Every time is a source time** (ms into the file as recorded); trim, cuts and items never move when another one is edited, and only the export maps source time to output time (`keptSegments`, `sourceToOutput`, `outputToSource`, `outputDurationMs`). Items are a discriminated union on `kind` (`redact`, `blur`, `pixelate`, `highlight` = spotlight: everything outside the box is dimmed), each with `{id, startMs, endMs, rect}` in source pixels. Text, images and audio clips are new members of `ItemSchema` (and `normalizeItem`, the graph and the preview); nothing else in the model changes. `normalizeProject` makes any project valid (items inside the source with a 100 ms minimum, cuts clamped to the trim, merged and widened over slivers shorter than 100 ms, a crop even-aligned inside the source, fades no longer than the result) and never throws; `applyCommand` is the reducer (add/update/remove item, trim, add/remove cut, crop, audio, fades, export options) and returns the same object for a no-op. `video-edit-history.ts` mirrors the screenshot editor's history, including gesture merging, so a drag or slider is one undo step.
- **Render graph (`edit-graph.ts`, pure).** `buildEditArgs(project, input, output, {filterScriptPath})` returns `{ args, filterScript }`. The graph: `[0:v] fps=<source fps or 30>,format=yuv420p` (MediaRecorder files are variable frame rate) -> each item in order on the SOURCE timeline (`enable='between(t,a,b)'` is source time because nothing is cut yet): redact = `drawbox` fill; blur = `split`, `crop`, `gblur`, `overlay`; pixelate = `split`, `crop`, `pixelize`, `overlay`; spotlight = four `drawbox` bands -> `crop` -> one `trim` + `setpts` per kept segment (and one `atrim` + `asetpts` from the same list, so audio and video stay in lockstep) -> `concat` -> fades (`fade`, `afade`) -> `scale` (even sizes, lanczos, only down) -> `format`. Audio is the cut source with `volume`, or `anullsrc` of the result's length when muted or when the source has no audio. GIF: `fps`, `scale`, `split`, `palettegen`/`paletteuse`, no audio, 960 px wide and 12 fps by default. Encoders: MP4 libx264 medium CRF 20 + AAC 160k + faststart; WebM libvpx-vp9 CRF 32 `-b:v 0` `-row-mt 1` `-cpu-used 2` + libopus. The graph is written to a file in a per-job temp folder and passed with `-/filter_complex <file>` (FFmpeg 7+; verified with the bundled 9.0.2), which keeps the command line short however many cuts there are (Windows limit 32k characters). Only numbers (printed by helpers that accept nothing else) and a `#rrggbb` colour enter the graph; the input is opened with `localInput` (`-protocol_whitelist file`).
- **Export (`edit-export.ts`, `video-projects/service.ts`).** `video:export {historyId, project, format}` resolves the source from history, probes it (the project is re-checked against the file's real size, length and audio), queues a job on the shared `JobRunner` (one ffmpeg job at a time with MP4 export and compression), and runs `runFileJob`: partial file, probe, `verifyEdit` (container, codecs, picture size, length), atomic rename, cleanup on cancel/failure. Progress is measured against the result's length (`outputDurationSec`). The new file is saved next to the source as `<name> (edited).<ext>` (`freeFileName`) and added to history with `derivedFrom` = the source (GIF as `type: recording`, `format: gif`, an `<img>` in History). Cancel is the existing `export:cancel`. Events: `video:exportProgress | exportDone | exportFailed`.
- **Store (`video-projects/store.ts`).** `<userData>/video-projects/<historyId>/project.json`: zod, atomic write, at most 512 KB, a damaged or newer-version file is renamed `project.corrupt-<time>.json` / `project.newer-<time>.json` (nothing is lost, the editor starts a new project). Removed with the history item by `HistoryService` (same path as screenshot projects: `deleteFile`, undo-window expiry, `clearMissing`, history overflow) and swept at startup when no item refers to it.
- **Renderer.** View `video-editor` (reached from History, not in the sidebar; the sidebar collapses like the screenshot editor's). `useVideoProject` opens the project, keeps the undo history and autosaves 600 ms after the last change (and when the editor is left; `App.tsx` writes pending changes first and asks only if that fails). `Player` drives the `<video>` and lives outside React (the playhead and time read-outs subscribe to it), skipping cuts and stopping at the trim end (`playback.ts`). `PreviewStage` puts a canvas over the video that draws the items active at the current time (blur with `ctx.filter`, pixelation by down- and up-scaling, spotlight with an even-odd fill), the crop as a dimmed border and the handles of the selection; the canvas is only drawn to, never read. `Timeline` is plain DOM (ruler ticks only for the visible range, so an hour costs the same as a minute; zoom, scroll, scrub, trim handles, hatched cuts, range selection, item rows packed so none overlap, snapping with Alt to disable). `Inspector` has the selected item or cut, crop, audio and fades; `ExportControls` the split button and progress.
- **Text, images, audio and frame rate (P9, ADR-044).** `ItemSchema` gained `text`, `image` and `audio`; audio clips have no box (`VisualItem` = every other kind). Text is drawn by `text-draw.ts` (line breaking in `text-layout.ts`): into the overlay canvas for the preview and, via `rasterizeText`, into a transparent PNG of the item's box that `video:export` carries as validated bytes (`overlays`). `edit-graph.ts` numbers the extra inputs with `plannedInputs` (every text and image item and every unmuted audio clip, in item order; none audio for a GIF): pictures are `-loop 1 -framerate <fps> -t <end>` inputs overlaid with `fade=...:alpha=1` and `enable`, audio clips are `atrim`/`adelay`ed and mixed with the original (or `anullsrc`) by `amix=normalize=0:duration=first` BEFORE the segment split, so the same cuts apply to picture and sound. Assets (`VideoProjectStore`: `writePicture`, `importAudio`, `pruneAssets`, `assetPath`) live in `<project>/assets/<sha256>.<ext>` and reach the preview by `framecapt-media://vproject/<history id>/<name>` (`media-protocol.ts`). New channels `video:addImage` (PNG bytes) and `video:pickAudio` (a main dialog, ffprobe checks, 100 MB cap). The recorder stores `fps` on the history item; `video:open` uses it, else `ProbeResult.frameRate` (`r_frame_rate` within 10..120 fps), else 30. The preview plays clips with `ClipAudio` (one `<audio>` per clip, synced by the `Player` as it plays, jumps and seeks). Tests: `edit-graph-overlays`, `video-edit-items`, `video-project-assets`, `video-edit-service-assets`, `video-assets-route`, `video-editor-text`, `edit-overlays-integration` (real ffmpeg: sampled frames and loudness), e2e `video-editor-overlays.spec.ts`.
- E2E: `tests/e2e/video-editor.spec.ts` (real UI and real ffmpeg: open, draw, cut, undo, restore, export MP4 and GIF, cancel, axe in both themes); unit: `video-edit-model`, `edit-graph`, `edit-integration` (real ffmpeg), `video-project-store`, `video-edit-service`, `video-editor-math`, IPC contract and security tests.

## Desktop layer: settings, shortcuts, tray, close-to-tray and quitting (phase 08: Implemented; unit, E2E and native runs)

A file that is not JSON, fails validation (including "two actions share a shortcut") or comes from a newer version is renamed `settings.json.corrupt-<time>`; defaults are used and the renderer is told once (`settings:consumeNotice`, a toast "Settings were reset because the file was damaged"). `migrateSettings` upgrades older shapes step by step; v0 (unversioned flat layout) is a tested scaffold for the mechanism, no such file was ever shipped. No credentials are stored.
- **IPC** (all `main` role): `settings:get | update | reset | chooseOutputDir | useDefaultOutputDir | openOutputDir | consumeNotice`, `shortcuts:status | validate | setPaused`, `app:resolveQuit`; events `settings:changed`, `shortcuts:changed`, `app:confirmQuit`, `app:startRequest`, `app:navigate`, `app:toast`. `settings:update` takes a validated one-level-deep partial; **the output folders are not part of it**: they are set only by `settings:chooseOutputDir` (a folder dialog in main, then a probe file is written and removed; an unwritable folder is refused with `OUTPUT_DIR_UNWRITABLE`). `toolbar:resize` (toolbar role) sizes the toolbar window.
- **What a setting changes**: `theme` -> `nativeTheme.themeSource` (every window follows through `prefers-color-scheme`) and `<html data-theme>`; `launchAtLogin` -> `app.setLoginItemSettings` only when the user toggles it and only in a packaged build (Squirrel installs register `Update.exe --processStart "<exe>" --process-start-args "--hidden"`, as the Electron docs prescribe, so updates keep working; a start with `--hidden` stays in the tray); `closeToTray`; `screenshots.format/jpegQuality` (Save/Ctrl+S), `afterCapture` (save before the editor opens; a saved capture starts the editor clean), `screenshots.autoCopy` and `recording.autoCopy` (the clipboard rule, ADR-049); `recording.saveFormat` and `recording.compression` (the post-save conversion, ADR-049); `recording.*` are the record options (the home strip edits the same values; the phase-05 localStorage options are migrated once, then the key is removed); `autoExportMp4` starts the MP4 export next to the recording when it is saved; the folders feed the save dialogs, recording finalization, recovery and the MP4 dialogs. A saved microphone that is gone is reported ("Saved microphone not found - using default"), never silently dropped.
- **Global shortcuts** (`ShortcutManager`): registers from settings at startup and on change. It remembers the accelerators it registered and unregisters only those (never `unregisterAll`: the countdown's Esc is another module's); `register` returning false (another app holds it) or throwing is a per-action status `ok | conflict | invalid | disabled` shown in Settings (`shortcuts:status`, `shortcuts:changed`) and on the home view. Duplicates are refused before saving and never registered twice. The shortcut recorder pauses all of them while it listens (`shortcuts:setPaused`), otherwise the pressed keys would be consumed by the global registration. Everything is released on `will-quit`.
- **One set of flows** (`actions.ts`): shortcuts, the tray and the buttons start the same `CaptureFlow.start` / `RecorderController.start`. Screenshot while a capture or recording runs: ignored with a message (BUSY). A record shortcut while recording stops it, during start-up it cancels; stop and pause/resume have their own. A window target (needs the picker) or an open editor (unsaved work: "Discard this screenshot?" first) is handed to the main window (`app:startRequest`). A capture cancelled while the main window was hidden in the tray leaves it hidden; a finished one shows the editor.
- **Tray** (`TrayController`): one icon for the app's life (`ensure()` is idempotent; tested). Icons are the owner's logo (see Brand assets below) at 16/20/24/32 px for 100/125/150/200 % scaling, with a red dot with a white ring at the bottom-right while recording, embedded as base64 so nothing extra is packaged. Menu: (while recording) Pause/Resume and Stop first, Screenshot and Record submenus with the configured accelerators as labels, Open FrameCapt, History, Settings, Quit. Tooltip "FrameCapt" or "FrameCapt - Recording 01:23" (the only timer, it runs only while recording). Left click opens the window.
- **Close-to-tray and quitting**: with `closeToTray` on (default) and a tray icon, closing the main window hides it; the first time a notification says "FrameCapt is still running in the tray" (remembered in `notices.trayHintShown`). `window-all-closed` keeps the app alive in that mode. Quit from the tray (or any `requestQuit`) while recording shows "A recording is in progress. Stop and save it before quitting?" [Stop & quit] [Keep recording] in the main window; Stop & quit calls `app.quit()` and the existing phase-06 `before-quit` path finalizes the recording (15 s cap). `before-quit` marks the app as quitting so windows then really close; "Keep editing" on the unsaved-screenshot question withdraws a quit. A second launch shows and focuses the window (also out of the tray).
- **Overlay readiness** (fix of the first-run drag flake): the overlay ignores pointer input until `overlay:ready` was answered (main shows the window while answering), exposes `data-ready`, and keeps the selection and gesture in refs so a handler never works from a stale render. Keyboard selection: an arrow key starts a centered selection; arrows move it, `Alt`+arrows resize it.
- **Toolbar size**: the toolbar pill is `w-max` and reports its measured width (`toolbar:resize`); main sizes the window to exactly that, centered on itself. Content can no longer be clipped. Finalization shows determinate progress ("Saving... 42 %", remux position against the active time).
- **Recording timestamps**: the remux now passes `-bsf setts=...` (`STRICTLY_INCREASING_TIMESTAMPS`): a packet whose timestamp would not move up is put one tick (1 ms) after its predecessor. Reason: MediaRecorder can stamp the first two frames within the same millisecond (observed: 2 of 30 recordings began `0, 0, 32, 65`); see decisions ADR-031.
- **Errors** (`shared/error-messages.ts`): one table of friendly copy with a next step for every error code the app produces (IPC, recorder, media tools, capture layer); a unit test scans the sources so a new code cannot be added without copy. Toasts go through `lib/notify.ts`.
- **E2E-only hooks** (compiled out of normal builds, listed in `scripts/check-no-mocks.mjs`): `globalThis.__frameCaptTest` (tray count, shortcut states, run an action, request quit, IPC call counters), `FRAMECAPT_E2E_FAKE_SHORTCUTS=1` (a stand-in for `globalShortcut`, so the suite never grabs real keys) and `FRAMECAPT_E2E_TAKEN_SHORTCUTS` (accelerators "another app" holds).

## Step guides (flow capture)

- **Detection without hooks.** `src/main/flows/flow-detector.ts` is a pure state machine fed `{x, y, t}` samples; `controller.ts` (`StepsController`: idle, active, paused, saving) polls `screen.getCursorScreenPoint()` every 100 ms only while a guide is captured (no timer, no hook while idle). A step is "moved more than 24 DIP from the last step (or first rest), then within 6 DIP for 700 ms, at least 1.5 s after the previous step". See ADR-045.
- **Capture.** The display under the pointer is grabbed with `grabScreensExact` (worker frame as fallback and in the mock build), written to `<userData>/flows/<session>/step-NN.png` with the pointer in that image's pixels (`cursorToFramePixels`, from the real frame size). Max 200 steps. Mutual exclusion is wired into the existing busy checks (`actions.ts`, `CaptureFlow.isBlocked`, the recorder's `isScreenshotBusy`, `AppServices.isBusy`, the tray).
- **The pill** is the recording toolbar's window and role (`createToolbarWindow(..., 'steps')`, URL `#/toolbar?mode=steps`, content-protected, always on top); the renderer shows `StepsPill` instead of `ToolbarView`. Main minimizes the main window while a guide is captured and restores it on Done or Cancel.
- **Saving.** `writeGuideFolder` fills a hidden temp folder (`step-NN.png`, `flow.json` v1 via zod) and renames it to `FrameCapt Steps YYYY-MM-DD at HH.MM.SS` in the screenshots folder; History gets a `flow` item (path = `flow.json`, format `flow`, thumbnail = first step with the ring burned in by `drawRing`, `stepCount`). The rescan also finds such folders (one level deep, valid `flow.json`).
- **Flow view** (`views/flow/`) reads and edits by history id: `flow:get`, `flow:update` (title, ordered file names + captions; names are checked against the guide's own files; a deleted step stays on disk for the 15 s undo window, then goes to the Recycle Bin), `flow:readStep`, `flow:openStepInEditor` (an editor session linked in main to the step; `shot:saveOver` writes that step atomically), `flow:export`. Step pictures are served by `framecapt-media://flowstep/<history id>/<index>` (PNG only).
- **Exports.** The renderer draws the pictures (ring, caption banner) and sends PNG bytes (checked, size-capped); main writes images, builds the HTML (`export-html.ts`) or runs the slideshow on the shared `JobRunner` (`slideshow.ts`: numbered frames read as an image sequence at 0.4 fps, MP4 `-r 30`, GIF `-r 10`; both measured, see the comments). The MP4 and the GIF are each added to History as derived from the guide.

## Packaging, installer and updates (phase 10)

- **Renderer origin.** Production loads `app://framecapt/index.html#/<role>`. `registerPrivilegedSchemes()` (`app-protocol.ts`, before `ready`) registers `app` (standard, secure; no CORS, no fetch API, no `bypassCSP`) and `framecapt-media` in one call; `registerAppProtocol(rendererDir)` answers requests from the built renderer directory (inside `app.asar` when packaged). `isAppUrl` accepts exactly the `app://framecapt` origin (dev: the Vite origin), so IPC sender checks, permission handlers, the display-media authorization and navigation lockdown all use it. Nothing loads from `file://`, which is why the fuse can be off.
- **Installer.** Electron Forge `maker-squirrel` (per-user, no UAC, `%LOCALAPPDATA%\FrameCapt`) and `maker-zip` (portable). FFmpeg ships as an extra resource (`resources/ffmpeg/win32-x64`). Identity (name, publisher, app id, placeholder icon) is PROVISIONAL. Signing is optional and environment-only; unsigned builds say so in the build log. See [packaging.md](packaging.md) and [release-process.md](release-process.md).
- **Lifecycle.** `squirrel.ts` handles `--squirrel-install/updated/uninstall/obsolete` (create/remove shortcuts, remove the launch-at-login entry, quit early) and lets `--squirrel-firstrun` start normally. The AppUserModelID is `com.squirrel.FrameCapt.FrameCapt` in a Squirrel install (so notifications match the Start Menu shortcut), else the provisional `com.framecapt.app`.
- **Updates.** `updates.ts` is an adapter over Electron's `autoUpdater` with the states unconfigured, idle, checking, available, downloading, ready and error. The feed URL is the build-time constant `__FRAMECAPT_UPDATE_URL__` (empty by default = `unconfigured`: `autoUpdater` is never even loaded and nothing touches the network). Nothing calls `checkNow()` yet. Settings > About shows "Updates: Not configured for this build". ADR-035.

## Brand assets and the boot screen

- **Pipeline.** `npm run brand:assets` (`scripts/generate-brand-assets.mjs`, dev-only, uses the `@napi-rs/canvas` devDependency) reads the owner's artwork `assets/brand/framecapt-logo-source.png` and writes every derived file, which are committed so a build never depends on running it. The source has a blotchy dark halo in its alpha channel, so the script rebuilds the alpha: bright pixels form a mask, a morphological closing (radius 14, running sums) fills the gaps, the background is flood-filled from the border, and the mask is feathered; the result is cropped and padded to a square (8 % margin). Sizes are made from the 1024 px master with a Lanczos-3 resampler on premultiplied alpha and, up to 32 px, a light unsharp mask so the red dot and the frame stay readable. There is no randomness, clock or font in it, so a second run gives byte-identical files (checked by hashing). Outputs: `assets/brand/framecapt-logo{,-512,-256}.png`, `assets/app/framecapt.ico` (16, 20, 24, 32, 40, 48, 64, 128, 256 px; PNG entries), `assets/app/install-loading.gif`, `assets/tray/*` and `src/main/tray-icons.generated.ts`, `src/renderer/assets/logo-{32,64,128,256}.png`. `tests/unit/brand-assets.test.ts` asserts sizes, the GIF budget and that the embedded tray PNGs equal the files.
- **Where the assets are used.** `forge.config.ts`: packager `icon`, Squirrel `setupIcon` and `loadingGif` (400x300, 24 frames, about 0.5 MB; shown by Setup.exe on interactive installs only). The main window gets `icon: assets/app/framecapt.ico` only when unpackaged (a packaged build uses the icon embedded in the exe). The renderer imports the PNGs through Vite (`components/Logo.tsx`, 1x/2x `srcset`); CSP `img-src 'self'` allows them.
- **Boot screen** (`MainApp.tsx`, `components/BootScreen.tsx`). Only the main window role renders `MainApp` (main.tsx); overlays, toolbar, countdown and recorder never contain it (asserted in the e2e suite), and `index.html` has no static loader markup. `MainApp` mounts the real `App` immediately (inert) and covers it until settings, shortcut status and the first history list have answered (a 6 s cap, so a failed load never traps the user), then fades out over 200 ms and unmounts. There is no minimum display time. `ready-to-show` does not wait for any of it: the window shows on the first paint with the theme-matched `backgroundColor`. prefers-reduced-motion shows a still picture (no glow, a half-filled bar). E2E builds only: `localStorage framecapt-boot-hold` plus a `framecapt:boot-release` window event hold and release the screen so a test can observe it.
- **Loader** (`components/Loader.tsx`). The logo mark in a rotating cyan-indigo-violet ring, sizes sm/md/lg, `role="status"` with a label (or `decorative` next to text that already announces the work). Used for finishing a recording, an MP4 export waiting to start, a recovery in progress and the window picker's first load (its skeleton grid stays). The ring and the boot bar are the only places the cyan-to-violet gradient appears; the accent remains indigo.

## Webcam overlay (phase P5)

- **Role `camera`** (`#/camera`, `views/camera/CameraView.tsx`): a frameless, transparent, always-on-top ('screen-saver' level), content-protected square window, created hidden when a recording with `options.camera` has passed preflight and shown (without focus) from the countdown until the recording ends or is cancelled. It shows a mirrored `getUserMedia` preview (640 x 480 ideal); the whole bubble drags (`app-region: drag`), hover controls (size S/M/L, shape, hide) opt out. Window side: S 160, M 220, L 300 DIP. Because it is content protected the bubble itself is never in the video; the recorder window composites the camera instead, so window and region recordings are right too.
- **Permissions** are role-aware (`app-origin.ts`): video requests only from `recorder` and `camera`; video checks (device labels) also from `main`.
- **Placement** (main, `recorder/camera.ts`, pure helpers in `shared/camera.ts`): the window's `move` event (throttled to ~30 Hz) and `moved` send `{ cmd: "camera", nx, ny, size, shape, visible }` to the engine. Screen and region recordings map the bubble center into the captured area (0..1; the bubble is kept inside it after a drag); window recordings snap the bubble to the corner of its display whose quadrant it was dropped in and send that corner (`cameraCorner` is remembered). Size, shape and corner changes are saved to the recording settings (`persistCameraStyle`).
- **Engine**: the camera is acquired before the display (a gone device falls back to the default camera; none at all is the preflight choice `camera-missing`: "Record without camera" or cancel). The compositor (`createCompositor({ camera })`; `createCanvasTransform` is the one-tile case, so every recording already goes through it) draws the camera last each tick at `cameraRect` (a square of 14/20/28 % of the output's shorter side, even aligned, kept inside with a margin), center-cropped, mirrored, clipped to a circle or rounded square, with a white ring and a soft shadow (`capture/camera-layer.ts`). A camera that is unplugged mid-recording only hides the overlay. The camera track is stopped in `releaseAll` with the other tracks.
- **Channels**: `camera:getStyle`, `camera:setStyle` (role `camera`), `recorder:toggleCamera` (toolbar). `recorder:state` carries `camera: { visible } | null` for the toolbar's camera button.
